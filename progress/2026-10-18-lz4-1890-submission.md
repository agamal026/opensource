## Compatibility problem and focused fix

[Issue #1889](https://github.com/lz4/lz4/issues/1889) requests support for the Linux kernel extension that terminates a legacy LZ4 frame with a four-zero-byte block-size header. The [upstream format document at the tested base](https://github.com/lz4/lz4/blob/e7c36223415219c0a18ea75e3fe2eb5d267ee667/doc/lz4_Frame_format.md) already describes this extension. The decoder previously treated that word as a zero-length compressed block and failed. The listing reader could continue treating block-like bytes after the marker as part of the preceding frame.

The production change consists of **three zero-size checks** in `programs/lz4io.c`: the separate threaded and nonthreaded legacy decoders, and the legacy listing reader. The decoders leave through their existing cleanup paths, preserving queued decoding/writing and the final sparse-output flush. Listing counts the four-byte marker before ending the frame. A following frame must start with its own magic number. The format documentation is reconciled with the existing kernel extension. No compression output, public API or ABI change is included. See the [independent automated review](https://github.com/agamal026/lz4/blob/9016232b3f5ef31764c6b4ae30f201da1ecaa445/contribution-review/1889/AUTOMATED_REVIEW.md) for the source-level reasoning and its limits.
